Batch 4 deviations:

1. **`ShareLinkDO.revoke()` is idempotent, not error-on-repeat.** Batch 4's first draft of the 6.1 integration test asserted that revoking an already-revoked share returns `NOT_FOUND` on the second call. That assertion was wrong: `share-link.ts`'s `revoke()` only checks `!row || row.owner !== owner || row.viewed` — it does NOT check `row.revoked`, so a second revoke on an unviewed, already-revoked share still matches and returns `true` again (this is Batch 1's real, intentional implementation, unchanged). Fixed the TEST to match the real (and reasonable — revocation is naturally idempotent) behavior instead of changing production code for a test-authoring mistake.
2. **The expiry/hard-delete scenario (6.1) is split across three separate HTTP routes (`/share-link-expiry-create`, `-reveal`, `-peek`) instead of one in-worker `sleep()` inside a single fetch handler.** First attempt used a single request that created a 2s-TTL share and `await sleep(2292)`'d before checking. Empirically, `wrangler dev --local` (workerd) silently truncates a long `setTimeout`-based wait the longer a single request has already been running: a fresh, first-in-request 2000ms `sleep()` measured *exactly* 2000-2002ms three times in a row, but the identical `sleep(2292)` measured only ~600-1830ms once ANY prior async work (even just account creation, unrelated to the DO/alarm) had already run earlier in the same request — cumulative wall-clock budget per request, not per timer, is the working theory (confirmed via a `/debug-sleep` vs. `/debug-sleep-with-account` A/B comparison, both removed before the final commit). Moving the wait to the Node-side test runner (real `setTimeout`, no such constraint, separate HTTP round-trips) fixed it deterministically and is arguably more realistic anyway — a real recipient's browser polls across page loads, not from inside one long-lived server request.
3. **Discovered, but did NOT fix (out of `allowedEditRoots`): `packages/worker/src/transport.ts`'s `WorkerReceiver`/`packages/worker/src/idempotency.ts`'s `IdempotencyStore` has a real bug that affects the share-view page's UX.** `_handlePost()` hashes the full raw request body and, on a repeat identical hash within a 1-hour TTL, unconditionally replays `{error: existing}` — even when the ORIGINAL request succeeded (a cached success's `code` field is `undefined`, since `store()` is called with `code: raw.error`, which is `undefined` on success; the replay still wraps it as an error). Anonymous `peekShare`/`revealShare` calls have no session/time/nonce field, so their raw body is identical across repeat calls with the same device fingerprint (stable per browser profile) and share id — meaning a real recipient reloading `/share/:id` a second time within an hour of their first visit gets this replay bug instead of the intended per-outcome state. Confirmed via direct raw HTTP calls against a live `wrangler dev` during the 6.2 manual walkthrough (see Issues Found for full reproduction). This is pre-existing, general-purpose transport code applied to every RPC method, not something introduced by `share-password`; it happens to be *exposed* by this feature because `peekShare`/`revealShare` are the only anonymous, no-auth, no-nonce RPC calls in the app that get invoked with a byte-identical body across multiple real invocations. The underlying single-view security guarantee (enforced independently at the `ShareLinkDO`/SQL layer, verified by 6.1's real, non-mocked integration test) is NOT affected — this is a UI-copy-selection bug (shows the generic "Link Not Available" instead of the more specific "Already Viewed"), not a data-leak or double-reveal risk.
4. **The Batch 3 icon deviation (`icon="unlock"` for "Share Link ...") stands, but a better existing candidate was found: `icon="show"` (the eye glyph, already used by `share-view.ts`'s own "Reveal" button, line 184).** Re-examined the icon set (`packages/app/src/elements/icon.ts`) as this batch's flagged follow-up required. `icon="show"` is a closer semantic match ("reveal a secret") than `icon="unlock"`, and is already established in this exact feature's own UI for exactly that meaning. Not applied: `packages/app/src/elements/item-view.ts` is outside this batch's `allowedEditRoots` (docs/debug-log-only scope was `server.ts`/`share-link.ts`). Left as an explicitly deferred, low-risk follow-up rather than an unauthorized edit.
