## Exploration: share-password (one-time, expiring, no-login share links for passwords)

### Current State

Padloc's entire sharing model today is **membership-based E2E encryption**, not public link sharing:

- `packages/core/src/container.ts` — `SharedContainer` (extends `BaseContainer`) encrypts a random AES-256 key once per container, then wraps that key with each accessor's RSA public key (`Accessor.encryptedKey`). This is how `Vault` (`packages/core/src/vault.ts`) and `Org` (`packages/core/src/org.ts`) share data among *authenticated, already-known* members — there is no concept of an anonymous recipient.
- Org membership invites (`packages/core/src/invite.ts`, handled in `packages/core/src/server.ts` `startAuthRequest`/`getInvite`/`acceptInvite`) are the closest existing "link" flow: the server emails an `acceptInviteUrl` (built from `config.clientUrl`, resolved at runtime from `env.CLIENT_URL` → `env.ALLOW_ORIGIN` → localhost, see `packages/worker/src/server-factory.ts:42-46`) plus a separate out-of-band confirmation code shown in `packages/app/src/elements/invite-view.ts`. Critically, **the invite link itself carries no secret/decryption material** — the invite payload (`invites.data` in D1) is encrypted with the *org's* invites key, and acceptance still requires the invitee to already have (or create) a Padloc account and be logged in. There is no "view without an account, single use" mechanism anywhere in the codebase.
- Grep across `packages/app`, `packages/core`, `packages/worker` for "share" turns up only: (a) the `SharedContainer`/`Org`/`Vault` membership-encryption machinery above, and (b) a mislabeled `icon="share"` on the **"Move To Vault ..."** action in `packages/app/src/elements/item-view.ts:517-529` and `packages/app/src/elements/items-list.ts:824` — this is item-to-vault relocation, unrelated to link sharing despite the icon name.
- **Conclusion: this is confirmed to be a genuinely new capability.** No public/unauthenticated link-sharing, no TTL-based secret reveal, and no "burn after read" primitive exist today in any package.
- The closest *reusable UI/interaction patterns* (not literal share-link components, since none exist) are:
  - `packages/app/src/elements/item-view.ts:521-529` — the `pl-popover` + `pl-list` "More Options" menu, the natural place to add a "Share Link ..." action next to "Move To Vault ..." / "Delete Item".
  - `packages/app/src/elements/dialog.ts` — generic `Dialog<Input, Output>` base class (`show(input): Promise<Output>`) used by every modal (`CreateInvitesDialog`, `ExportDialog`, etc.) — the natural base for a new `ShareDialog`.
  - `packages/app/src/elements/export-dialog.ts` — closest structural precedent for "pick options then produce a protected artifact" (format `pl-select`, `prompt()` for a password, `saveFile`).
  - `packages/app/src/elements/clipboard.ts` (`pl-clipboard`) and the mask/reveal pattern in `packages/app/src/elements/field.ts` — reusable for showing the generated link and for the recipient's one-time reveal.
  - `packages/app/src/elements/invite-view.ts` — precedent for a "confirmation code communicated separately" pattern, relevant if we want a two-factor share (link + separate short PIN).
- Client-side crypto primitives already available (`packages/core/src/crypto.ts`, `packages/core/src/container.ts`, `packages/core/src/platform.ts` `CryptoProvider`): AES-256-GCM (`AESEncryptionParams`, `getProvider().encrypt/decrypt`), CSPRNG (`getProvider().randomBytes`), symmetric key generation (`getProvider().generateKey(new AESKeyParams())`), and `SimpleContainer` — a container whose key is passed in explicitly rather than derived — is the exact primitive needed for a link-embedded key scheme.
- `packages/worker/src/index.ts` fetch handler is **not a generic REST router**: it special-cases only `GET /healthcheck`, then funnels everything else through a single RPC dispatcher (`WorkerReceiver.handleFetch` → `server.handle(req)`). `packages/core/src/api.ts` defines the RPC surface as an `API` class with `@Handler(InputType, OutputType)`-decorated methods; `packages/core/src/server.ts` `Controller.authenticate()` (line 199) only binds a session `if (req.auth)` — **individual handlers opt into auth by calling `this._requireAuth()` (line 2075)**, e.g. `getInvite` (line 1701) does, `createAccount` does not. This means a genuinely public, no-login RPC method is a first-class, already-proven pattern here (not a special case requiring new raw HTTP routes).
- D1 schema (`packages/worker/src/storage/schema.ts`) already has a **TTL + one-time-consume table precedent**: `email_verifications` (lines 230-247) stores `expires_at` (ISO 8601) and `consumed_at` (NULL until consumed) for one-time email codes. There is no existing generic `Storage` interface method for an atomic conditional "consume" write, though — `packages/worker/src/storage/d1.ts`'s `Storage` implementation is get/save/delete (read-modify-write) style; the actual one-time-consume logic for `email_verifications` would need checking in `packages/core/src/server.ts`/`auth/email.ts` before assuming its atomicity — it was NOT verified as part of this exploration and should not be copied blind.
- Durable Objects are already used for consistency-critical, per-entity coordination: `packages/worker/src/locks/account-lock.ts` (`AccountLockDO`) serializes concurrent requests per account/org id via an in-memory FIFO promise chain, bound in `packages/worker/wrangler.toml` (`[[migrations]] tag="v1" new_classes=["AccountLockDO"]`, `[[env.dev.durable_objects.bindings]]`). Note it uses legacy (`new_classes`, non-SQLite) DO storage — a new DO class for shares should use `new_sqlite_classes` per current best practice (see Durable Objects skill).
- `packages/worker/src/idempotency.ts` and `packages/worker/src/rate-limiter.ts` show the existing KV (`env.HINTS`) usage pattern: `kv.put(key, value, { expirationTtl })`. **Cloudflare KV is eventually consistent and has no compare-and-swap** — this matters directly for the one-time-view atomicity decision (see Approaches/Risks below).
- `packages/core/src/server.ts` `ServerConfig extends Config` (line 70) already has multiple `@ConfigParam()` fields (e.g. `clientUrl`, `maxRequestAge`) — new share-related config (e.g. `shareLinkMaxTtlSeconds`, `shareLinkDefaultTtlSeconds`) can be added as fields on this *existing* class. Per `padloc-worker-decorator-tsconfig-crash`, the startup crash only triggers when a **new class extends** `Config`/`Serializable` inside `packages/worker` under a `tsconfig.json` missing `experimentalDecorators: true` — adding fields to the existing `ServerConfig` (which lives in `packages/core`, already compiled with `experimentalDecorators: true` at the repo root) is safe. Any *new* `packages/worker`-local class using `@ConfigParam`/`@AsSerializable`/`@AsBytes` (e.g. a worker-local params/response class for the new RPC methods) must be checked against `packages/worker/tsconfig.json` for `experimentalDecorators: true` before assuming it's safe.
- PWA is a single-bundle SPA (`packages/pwa/src/index.ts` mounts one `<pl-app>`), routed entirely client-side by `packages/app/src/elements/app.ts` `handleRoute()`. That gate (lines 116-129) already allow-lists **pre-auth pages** (`start`, `login`, `signup`, `recover`) that render before `app.state.loggedIn`/`app.state.locked` — i.e. the SPA already supports fully unauthenticated routes as a first-class concept. A new `/share/:id` (or similar) destination page fits this exact pattern; it must be added to `_pages` (line 51-64) and to the pre-auth allow-lists at both `app.ts:117` and `app.ts:122` (and skip the `unlocked` wrapper toggle at line 137-138) so it renders standalone without requiring login, unlock, or even an existing account.

### Affected Areas

- `packages/core/src/api.ts` — add new `@Handler`-decorated RPC methods to `API` (e.g. `createShare`, `getShare`) and their param/response `Serializable` classes.
- `packages/core/src/server.ts` — implement the new handlers on `Controller`; `createShare` needs no `_requireAuth()` only if fully anonymous sharing from a non-logged-in sender is desired (unlikely — sender must be logged in to have an item to share; **recipient view is what must be anonymous**), so `createShare` likely calls `_requireAuth()` while `getShare`/`viewShare` deliberately does not.
- New file, e.g. `packages/core/src/share.ts` — a `Share`/`ShareLink` `Serializable`/`Storable` model (id, ciphertext blob + `AESEncryptionParams`, `expiresAt`, `maxViews`/`viewedAt`, no plaintext, no key).
- `packages/worker/src/storage/schema.ts` + `packages/worker/src/storage/d1.ts` — new `shares` table (id, encrypted_data, encryption_params, expires_at, consumed_at/viewed_at, created_at) and, if the D1-conditional-update approach is chosen, a bespoke atomic consume query outside the generic `Storage` get/save/delete abstraction.
- `packages/worker/wrangler.toml` + `packages/worker/src/env.ts` + `packages/worker/src/index.ts` — if the Durable-Object atomicity approach is chosen instead: new `ShareLinkDO` class, `[[migrations]] new_sqlite_classes=["ShareLinkDO"]`, new DO binding, exported from `index.ts` alongside `AccountLockDO`.
- `packages/core/src/server.ts` `ServerConfig` — new `@ConfigParam()` fields for min/max/default TTL and (optionally) max-views policy.
- `packages/app/src/elements/item-view.ts` (and `items-list.ts`) — new "Share Link ..." entry in the existing "More Options" `pl-popover`.
- New file `packages/app/src/elements/share-dialog.ts` (extends `Dialog<VaultItem, void>`) — TTL picker (`pl-select`), generate link, `pl-clipboard` copy-to-clipboard, styled per `export-dialog.ts`/`create-invites-dialog.ts` conventions.
- New file `packages/app/src/elements/share-view.ts` (or similar) — the anonymous, no-login recipient page; registered as a pre-auth route.
- `packages/app/src/elements/app.ts` — add the new page to `_pages` (line 51-64) and to both pre-auth allow-lists (lines 117, 122); ensure the URL-fragment key (`window.location.hash`) is read before any router logic that might strip/rewrite it.
- `packages/core/src/crypto.ts` / `packages/core/src/container.ts` — likely reused as-is (`SimpleContainer`, `AESEncryptionParams`, `getProvider().generateKey/encrypt/decrypt`); no changes expected unless a KDF is added for an optional "extra passphrase" layer.
- `packages/worker/src/rate-limiter.ts` — the anonymous `getShare`/view endpoint is a prime brute-force target (guessable share IDs) and needs rate limiting distinct from the existing per-IP config.
- `config/environment-targets.json` / AGENTS.md Hosting section — the share link's base URL must be built from `config.clientUrl` exactly like `acceptInviteUrl`, never hardcoded.

### Approaches

**A. Crypto / key-distribution scheme for the shared secret**

1. **URL-fragment-embedded symmetric key (1Password-style)** — Client generates a random AES-256 key via `getProvider().generateKey(new AESKeyParams())`, encrypts the serialized `VaultItem` (or just the target field) using a `SimpleContainer`, uploads only `encryptedData` + `encryptionParams` to the server, and builds the link as `https://<clientUrl>/share/<id>#k=<base64url(key)>`. The `#fragment` is never sent to the server by browsers (not included in HTTP requests), so the server/DB never sees plaintext or the key — matching 1Password's Psst! model exactly.
   - Pros: True zero-knowledge — server compromise never exposes shared secrets; no new KDF needed (reuses existing `AESKey`/`AESEncryptionParams`/`SimpleContainer` primitives verbatim); matches user's explicit 1Password reference; link itself is the "password" (nothing else to communicate).
   - Cons: If the link leaks via referrer headers, browser history, or link-preview bots (Slack/Discord unfurling) before the real recipient opens it, the key is exposed — but this is inherent to *any* link-based scheme, not specific to this approach, and 1Password ships it anyway; requires care that the recipient page never triggers a network request containing the fragment (e.g. analytics scripts) and that no server-side link preview/OpenGraph fetch is added.
   - Effort: Low — pure reuse of existing `crypto.ts`/`container.ts` primitives, only new glue code (encode/decode key to/from `location.hash`) is genuinely new.

2. **Server-held key + separate PIN/passphrase communicated out-of-band** — Server generates and stores the encryption key itself (or derives it from a low-entropy PIN via PBKDF2, mirroring `PBES2Container`); the link alone is insufficient, recipient must also receive a short code separately (mirrors the existing `invite-view.ts` "confirmation code communicated separately" UX).
   - Pros: Familiar UX precedent already exists in this codebase (`invite-view.ts`); mitigates the "link leaked to a bot/history" risk since the PIN is a second channel; PIN can be short/memorable for verbal sharing.
   - Cons: Server (or its operator) can technically reconstruct the plaintext if it also stores/derives the key — breaks the zero-knowledge guarantee the user explicitly wants ("como 1Password"); adds UX friction (two things to send instead of one link) that contradicts the "link that just works" ask; PBKDF2 on a short PIN is weak against a server-side brute force unless iteration count is very high, which conflicts with fast unauthenticated access.
   - Effort: Medium — needs a new KDF-backed container variant and a second delivery channel UI, more surface area than reusing `SimpleContainer` directly.

**B. One-time-view atomicity mechanism (guarantee exactly one successful reveal even under concurrent requests)**

1. **D1 conditional UPDATE...WHERE...RETURNING on a `shares` table** — `UPDATE shares SET consumed_at = ?, viewed_at = ? WHERE id = ? AND consumed_at IS NULL AND expires_at > ? RETURNING encrypted_data, encryption_params` (D1/SQLite supports `RETURNING`); the request that gets a row back is the sole winner, any concurrent duplicate gets zero rows back → 404/410. D1 serializes writes per database, so this is atomic without extra infrastructure. Mirrors the existing `email_verifications.consumed_at` TTL/one-time pattern already in `schema.ts`, just needs the atomic conditional query added (the generic `Storage` get/save/delete interface in `d1.ts` doesn't support this — needs a bespoke method, same class of exception the `email_verifications` consume flow already required to be checked/likely already needed).
   - Pros: No new Cloudflare primitive (D1 is already provisioned and bound); directly extends an existing schema convention; cron-based cleanup of expired rows can reuse the existing `orphan_log`-style janitor pattern already present in `schema.ts`.
   - Cons: Bypasses the generic `Storage` abstraction (`packages/core/src/storage.ts`) that every other domain object uses — introduces a worker-local special case; correctness depends on D1's documented single-writer-per-database serialization holding under all conditions (regional read replicas / future D1 changes are a latent risk to watch).
   - Effort: Low — one migration, one bespoke method in `d1.ts`, reuses existing patterns almost entirely.

2. **Durable Object per share link (`ShareLinkDO`, SQLite-backed)** — One DO instance `idFromName(shareId)` holds the encrypted blob, `expiresAt`, and a `viewed` flag in its own transactional SQLite storage (`ctx.storage.sql`); `view()` RPC method checks-and-flips `viewed` and returns the blob or throws, all within the DO's single-threaded execution model (no read-modify-write race is even possible, unlike a table shared across all shares). An alarm (`ctx.storage.setAlarm(expiresAt)`) self-deletes the object on expiry, which also solves cleanup without a cron job. Mirrors the exact per-entity, strong-consistency pattern this codebase already established with `AccountLockDO`.
   - Pros: Cloudflare's textbook use case for DOs (per-entity strong consistency, see `durable-objects` skill); atomicity is structural (single-threaded per instance), not query-shaped, so it's harder to get wrong; built-in TTL cleanup via alarms, no janitor cron needed; naturally sharded (one DO per share, no lock contention across unrelated shares, unlike a shared `AccountLockDO`-style table).
   - Cons: New infrastructure (new DO class + migration + binding) vs. reusing D1 that's already fully wired; one DO per share is more objects to reason about/observe than rows in one table; per the `padloc-worker-decorator-tsconfig-crash` skill, if the DO's RPC method signatures use `@AsSerializable`/`@AsBytes` core classes, `packages/worker/tsconfig.json`'s `experimentalDecorators: true` must already be set (it is, per that skill's fix having presumably landed) — must be re-verified, not assumed, when this is implemented.
   - Effort: Medium — new DO class, wrangler migration/binding, but the `AccountLockDO` file is a ready-made template to copy from.

Ruled out: **KV with `expirationTtl`** (matching the existing `idempotency.ts`/`rate-limiter.ts` usage) — Cloudflare KV is eventually consistent globally and has no compare-and-swap/conditional-write primitive, so two near-simultaneous view requests hitting different edge locations could both read "not yet consumed" before either write propagates, violating the hard single-view guarantee the user explicitly asked for. This is a correctness disqualifier, not just a style preference.

### Recommendation

Combine **A.1 (URL-fragment-embedded key)** with **B.2 (Durable Object per share)**:

- A.1 is the only option that satisfies "que sean de 1 solo uso/view... como 1Password" *and* zero-knowledge simultaneously — it needs no new crypto primitives, just wiring already-proven `SimpleContainer`/`AESEncryptionParams` through a URL fragment.
- B.2 gives the single-view guarantee the user's ask is structurally strict about ("de 1 solo uso") without inventing a new consistency mechanism — it reuses the exact pattern (`AccountLockDO`) this codebase already trusts for exactly this class of problem (strong per-entity consistency on Cloudflare), and its alarm-based expiry directly implements "que estas expiren en el tiempo q se disponga" without a separate cron job.
- If a future reviewer prefers to avoid new DO infrastructure, B.1 (D1 conditional UPDATE) is an acceptable fallback with a clearly smaller footprint — both should be presented to the user/proposal step as the two real contenders (KV is disqualified outright, see above).

### Risks

- **Link-leak vector inherent to A.1**: chat apps/messaging clients that auto-fetch link previews (Slack, Discord, iMessage) could consume the one-time view before the intended recipient opens it, since a HEAD/GET from a bot is indistinguishable from a real view at the HTTP layer. Mitigation to design in the proposal: consider not resolving/burning on `GET`, only on an explicit user action (e.g. a "Reveal" button click that POSTs), and/or serving a static, no-JS-required interstitial for bots that never triggers the burn.
- **Rate-limiting / enumeration**: share IDs must be high-entropy (not sequential/short) since the recipient endpoint is unauthenticated by design; add to `packages/worker/src/rate-limiter.ts` config explicitly for this route, distinct from the general per-IP limit, to slow brute-force guessing.
- **PWA fragment handling**: the SPA's router (`packages/app/src/mixins/routing.ts`) must be verified to never log, forward, or strip `location.hash` before the share-view element reads the key — was not traced end-to-end in this exploration and needs a dedicated check during design/implementation.
- **D1 atomic-consume correctness (if B.1 chosen)**: the claim that `UPDATE ... WHERE consumed_at IS NULL ... RETURNING` is race-free depends on D1's single-writer-per-database model; this exploration did not independently verify Cloudflare's current documented guarantees and this must be confirmed against current D1 docs (per the `cloudflare`/`d1` skill's retrieval-over-pretraining rule) before implementation, not assumed from this report.
- **New worker-local `@AsSerializable`/`@ConfigParam` classes**: any new class in `packages/worker` that extends `@padloc/core`'s `Config`/`Serializable` (e.g. a `ShareLinkDO` RPC payload type, if it reuses core decorated classes) must be checked against `packages/worker/tsconfig.json`'s `experimentalDecorators` setting before shipping — this exact mistake has crashed the whole worker at startup before (see `padloc-worker-decorator-tsconfig-crash` skill). Adding plain fields to the existing `ServerConfig` is safe and does not trigger this.
- **`email_verifications.consumed_at` atomicity was not independently verified** — this exploration cites it as a schema precedent for TTL+one-time-consume, but the actual consume code path (likely in `packages/core/src/auth/email.ts` or `server.ts`) was not read; do not assume it is race-free without checking, and do not blindly copy its pattern without that check.
- **Deploy/PR process constraint** (non-blocking, just a process note per `AGENTS.md`): this repo forbids GitHub PRs — work must go to a topic branch with exact-SHA CI, then fast-forward to `main`. Not an implementation risk, but must be respected by whichever phase actually ships this change.

### Ready for Proposal

**Yes.** The codebase confirms this is a new, well-scoped capability with no conflicting existing "share link" feature to reconcile. Two concrete, evidence-based approaches are identified for both the crypto scheme (fragment-embedded key vs. server-held key + PIN) and the atomicity mechanism (D1 conditional update vs. Durable Object), with a clear recommendation and explicit disqualification of the unsafe KV-TTL option. The orchestrator should tell the user: exploration found no pre-existing share-link feature to build on (confirmed only membership-based E2E sharing exists today); recommend proceeding to `sdd-propose` with the fragment-key + Durable-Object combination as the default direction, flagging the link-preview-bot burn risk and the D1-vs-DO tradeoff as the two open decisions for the proposal to settle explicitly.
